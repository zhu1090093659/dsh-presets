# Agent Note: SDK cohort 0.2.1-rc.2

Status: implemented

## Problem

[2026-10-17-sdk-cohort-0.2.1-alpha.5](2026-10-17-sdk-cohort-0.2.1-alpha.5.md)
moved this repository to `0.2.1-alpha.5` the same morning; the official host
and npm `next` have since advanced to `0.2.1-rc.2`, and the family follows.
This note owns the rc.2 move and supersedes none of the alpha.5 record.

The move is not a pure re-literal. The alpha line carried alpha vendor
builds (`cordis 4.0.5-alpha.2`, `schemastery 3.18.5-alpha.2`,
`cosmokit 1.8.6-alpha.2`, `cordis-plugin-*-alpha.2`); rc.2 rides the formal
releases (`cordis 4.0.5`, `schemastery 3.18.5`, `cosmokit 1.8.6`), and the
`@deepseek-ai/cordis` devDependency moves off the stable line it shared with
the old cohort (`^4.0.4`, which could not see the alpha builds) onto
`^4.0.5`.

## Decision

The whole cohort moves to `0.2.1-rc.2` in one change, on the same local
branch as the alpha.5 move. No version bump, no publish, no push.

**One cohort, one literal.** `dsh.engines.dsh` (`>=0.2.1-rc.2`), the
`@deepseek-ai/dsh` host peer, and the seven consumed SDK devDependencies move
together; the README badge in both languages moves to the shields form
`0.2.1--rc.2` with `README.i18n.yaml` re-recorded.

**Vendor alignment by actual resolution.** The lockfile was rebuilt from a
clean resolution (`pnpm clean --lockfile` — the supply-chain gate rejects a
lockfile whose entries the ledger no longer covers, so re-resolution from
`package.json` is the prescribed path, not incremental lockfile edits). The
resolution lands exactly on the formal vendor set: `cordis 4.0.5`,
`schemastery 3.18.5`, `cosmokit 1.8.6`, `cordis-plugin-include 1.0.10`,
`cordis-plugin-loader 1.0.6`, `cordis-plugin-group 1.0.5`,
`cordis-plugin-timer 1.1.7`, `node-addon-system 0.1.2` and
`libreoffice-kit 0.1.5`; zero `@0.2.1-alpha.5` entries remain. The
`@deepseek-ai/cordis` devDependency becomes `^4.0.5`; `@deepseek-ai/dsh`
itself resolves at rc.2 like the rest of the family.

**The ledger followed the resolution by itself.** pnpm's exclude maintenance
union-appended the formal versions onto the alpha rows
(`@4.0.4 || 4.0.5-alpha.2 || 4.0.5`, `@3.18.5-alpha.2 || 3.18.5`, and the
cordis-plugin/cosmokit rows likewise), preserving the file's append-only
union style, and appended the rows for packages new in the rc.2 graph (for
example `dsh-client-ui-deepseek-model-label-1017`, `dsh-web-deepseek-api`).
The reconciliation script then proved the ledger covers exactly the resolved
`@deepseek-ai/*` set with no missing exclusions.

**The consumed registry API and the shell table are unchanged from alpha.5.**
`@deepseek-ai/dsh-agent-preset-registry@0.2.1-rc.2` declarations are
byte-identical to the alpha.5 tarball (registry class, `PresetDefinition`,
`AgentPreset`), so the plugin's `register`/`list`/`defaultId` seam needs no
repair. The published `dsh-web-frontend@0.2.1-rc.2` dist bundle carries the
same eleven-row `staticModules` table as alpha.5, so
`shared/web-platform.ts` keeps its list and moves only its provenance
comment.

## Alternatives considered

**Keep `@deepseek-ai/cordis` at `^4.0.4` and let the lockfile pair it with
the cohort's transitive 4.0.5.** Rejected: that is the alpha.5 arrangement,
which resolved two cordis builds side by side; the point of the vendor
alignment is one formal cordis for both the declared devDependency and the
cohort, so the range moves to `^4.0.5` and the graph resolves a single
4.0.5.

**Rewrite the union rows to only the formal versions.** Rejected: the union
rows are pnpm's own maintenance form and append-only history of what the
graph resolved across cohorts; pruning members buys nothing (exclusions for
uninstalled versions are inert) and fights the tool that owns the file.

**Patch around the unpublished dependency instead of waiting for upstream.**
Rejected, and moot: `dsh-web-app@0.2.1-rc.2` pins
`dsh-client-ui-settings-account@0.2.1-rc.2`, which existed in metadata before
its tarball propagated; a `pnpm.overrides` pin to rc.1 would have moved the
family off the cohort literal for a transient registry skew. The gap closed
in minutes (version published, then the tarball 404 cleared), the prescribed
clean re-resolution ran, and no installed file was patched.

## Consequences

- `pnpm install --prefer-offline` rebuilt the lockfile from a clean
  resolution; `pnpm typecheck`, `pnpm build`, `pnpm test` (55 tests),
  `pnpm preset:check` (32 presets), the catalog contract suite (`node --test
  scripts/preset-catalog.test.mjs`, 9 tests) and the CI supply-chain form
  (`pnpm install --frozen-lockfile --ignore-scripts`) all pass on the
  committed tree. The rebuilt `lib/` is byte-identical, so the committed
  artifact stays valid across both cohort moves.
- The transition recipe is now recorded twice: when the declared cohort and
  the committed lockfile part ways, the supply-chain gate stops the
  incremental path; `pnpm clean --lockfile` plus a fresh install (after any
  upstream publish gap closes) is the way through.
- Nothing was published and no `@linxin666/*` version changed; integrating
  the branch is a maintainer decision, as is moving the dsh-web submodule
  pin afterwards.
