# Contributing

This repository owns two things:

- **`presets/`** — the community agent-preset catalog. `catalog.json` plus one
  directory per preset is the publishing source the dsh-web market build reads
  from the pinned submodule; a preset merged here reaches every user of the
  Workshop's **Presets** panel.
- **the plugin itself** (**`@linxin666/dsh-client-ui-preset-center`**) — the
  Workshop panel and the host library that installs, declares, disables and
  uninstalls those presets.

Both live here since the plugin left the `dsh-web` monorepo. That repository
consumes the published npm package and pins this repository's `presets/` by
submodule commit.

## Adding a preset

1. Copy `presets/_template/` to `presets/<id>/`. The directory name is the
   preset id: it must match `^[a-z0-9][a-z0-9-]*$` and may not be a
   harness-shipped id (`minimal`, `ptc`, `standard`, `cordis`).
2. Fill `preset.yml`. `name` is required; `description` and `order` are
   optional. Every value stays on a single line.
3. Write `agent.cordis.yml`. A preset is code, not an asset: the composition
   may mount npm plugins, load files that travel inside the preset directory,
   and evaluate `!!js` expressions — all inside the DSH host process once the
   user declares it. Say in the pull request what it loads and why.
4. Append one entry to `presets/catalog.json` with `id`, `author` and
   `version`; `nameEn`, `descriptionEn`, `category`, `tags`, `rank` and
   `repo` are optional. `category` may only name a known category id
   (`roleplay`) and is left out otherwise.
5. Run the gate and the tests:

   ```sh
   pnpm install
   pnpm preset:check
   node --test scripts/preset-catalog.test.mjs
   ```

   The gate mirrors what the dsh-web market build enforces when it reads this
   repository, so a green run here is what keeps the pin safe to move.

The full publishing contract — the composition rules, the evidence a
submission must carry and the confirmation gate users see — is in
[presets/README.md](presets/README.md).

## Changing the plugin

```sh
pnpm install
pnpm typecheck
pnpm test
pnpm build
```

`src/` is split into `src/index.ts` (host half), `src/client/` (browser half)
and `src/core/` (shared logic); files carrying a
`// Generated by scripts/sync-shared.mjs` header are vendored copies of the
family's shared runtime modules — do not edit them here.

`lib/` is committed: `main`, `exports` and `files` all point at those bytes, so
a consumer that installs the package without rebuilding gets exactly what the
repository carries. After changing `src/`, run `pnpm build` and commit the
rebuilt `lib/` in the same commit; CI rebuilds and fails when the committed
output no longer matches the sources.

## Commit and review

Use Conventional Commits (`feat(presets): ...`, `fix(preset-center): ...`,
`docs(...)`). Do not use emoji in code, comments, documentation, or commit
messages. Keep changes to one preset per commit where practical so the diff is
reviewable.

## Release

The version is per-repository: it advances here and no longer with the dsh-web
monorepo. To cut a release, bump `version` in `package.json`, add the matching
`docs/release-notes/vX.Y.Z.md`, commit both, then push the tag:

```sh
git tag vX.Y.Z
git push origin vX.Y.Z
```

The tag is the release switch. `.github/workflows/release.yml` reruns the CI
gates, refuses to publish when `package.json` disagrees with the tag, publishes
to npm, verifies the version resolves from the registry, and creates the GitHub
Release. It needs the repository secret `NPM_TOKEN` (an npm automation token for
the `@linxin666` scope).
